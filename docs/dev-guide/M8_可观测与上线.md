# M8 可观测性与生产上线 —— 开发指引与验收文档

> 周期 W15–W16 ｜ 主轨 B（债务阶段 4）｜ 对应架构阶段 C5
> 一句话目标：**线上出问题，5 分钟内能说清「哪一步、哪个模型、多少钱」。**

---

## 1. 目标与范围

**做**：OTel 全链路（自动埋点 + 自定义 span）、GenAI 语义约定、Prometheus + Grafana 四块看板、五类告警（每类演练触发一次）、Langfuse 自托管接 OTLP、SLO + 错误预算、灰度发布与一键回滚、安全收尾（密钥/脱敏/依赖扫描/备份恢复演练）、runbook。

**不做**：云 APM 采购、多环境 K8s 部署、混沌平台（手动 kill 容器已够用）、告警值班体系（单人项目只做触达演练）。

## 2. 技术选型详述

### 2.1 OpenTelemetry（统一可观测内核）

- **自动埋点**：`opentelemetry-instrumentation-fastapi / sqlalchemy / httpx` 三件套覆盖 90% 调用路径；**自定义 span**：解析/抽取/规则/LLM 四个业务步骤手动包 span（这是"哪一步慢"的答案来源）。
- **导出**：OTLP → Collector → 后端（Grafana Tempo 链路 / Prometheus 指标 / Loki 日志）。Collector 是解耦层——换后端不改应用代码。
- **采样**：10% 常规采样 + **错误全采**（`parentbased_traceidratio + always_on for error`）——100% 采样在单机是自伤。
- **⚠️ GenAI 语义约定（2026 事实标准）**：span 属性 `gen_ai.provider.name`（注意 v1.37 起 `gen_ai.system` 改名）、`gen_ai.request.model`、`gen_ai.usage.input_tokens/output_tokens`、耗时。**prompt 内容默认不采集**（放 span events 且需显式开关 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`）——合同是敏感数据，本项目**默认关**，只采元数据；需要时开开关 + Collector 脱敏中间件。

### 2.2 指标栈：Prometheus + Grafana（自托管零成本）

- 指标红线：**禁止把 `contract_id`/`user_id` 当标签**（基数爆炸打爆 Prometheus）；高基数信息走 trace 与日志，指标只留聚合维度（endpoint/模型/状态/阶段）。
- Grafana 四块看板：① 流量与延迟（QPS/P50/P95/P99 分接口）② 任务与队列（成功率/堆积/重试/DLQ）③ **LLM 成本**（token 与费用，按模型/按 prompt 版本聚合）④ 业务漏斗（上传→解析→抽取→审查→审批转化）。

### 2.3 Langfuse 自托管（LLM 专属观测）

- MIT 核心自托管；OTLP 打通后 **prompt 版本 ↔ trace ↔ 成本** 三方可关联——回答"这次抽取消耗为什么涨了？是不是 prompt v4 变长"。
- 为什么不用 LangSmith：绑定 LangChain 生态，本项目不用 LangChain（ADR-0001）。

### 2.4 SLO 与错误预算

- SLO 示例：**可用性 99.5%**（月度，healthz 口径）；审查任务成功率 ≥ 99%；同步接口 P95 < 300ms。
- 错误预算 = (1 − 99.5%) × 月窗口：预算烧完 → 冻结功能开发、专修稳定性（纪律写进 README）。

### 2.5 发布：不可变镜像 + 灰度 + 一键回滚

- 镜像 tag = git sha（不可变，禁 `latest` 上生产）；灰度先 10% 流量（Nginx weight）观察错误率/P95 → 全量。
- 回滚 = 切回上一个 tag（compose 一条命令）——**发布脚本必须演练过回滚才算会发布**。

### 2.6 安全收尾清单

密钥全部走环境变量/Secret（代码零硬编码，`gitleaks` 扫描进 CI）；PII 脱敏白名单（日志与 trace 中合同主体名/金额按需掩码）；`pip-audit` + `trivy` 高危清零；**备份恢复演练**：`pg_dump` 定时 + MinIO 数据备份，恢复实测 **RTO < 30min**。

## 3. 详细设计（伪代码级）

### 3.1 自定义业务 span（手动埋点模板）

```python
from opentelemetry import trace
tracer = trace.get_tracer("contractforge.review")

async def review_pipeline(contract_id):
    with tracer.start_as_current_span("review.rules") as span:      # 规则通道
        span.set_attribute("rules.count", len(enabled_rules))
        rf = run_all_rules(ctx)
        span.set_attribute("rules.findings", len(rf))
    with tracer.start_as_current_span("review.llm") as span:        # LLM 通道
        span.set_attribute("gen_ai.provider.name", provider)
        span.set_attribute("gen_ai.request.model", model)
        span.set_attribute("gen_ai.usage.input_tokens", u.in_)      # 语义约定字段
        span.set_attribute("gen_ai.usage.output_tokens", u.out)
        span.set_attribute("prompt.version", prompt.version)        # 自定义维度
        lf = await llm_review(...)
    with tracer.start_as_current_span("review.aggregate") as span: ...
```

### 3.2 告警规则（每条都要演练触发一次）

| 告警 | 条件（PromQL 意图） | 触达 | 演练方式 |
|---|---|---|---|
| 错误率突增 | 5min 内 5xx rate > 5% | IM/邮件 | 临时注入异常路由 |
| P95 回归 | api P95 > 1s 持续 10min | IM | 灌入慢查询样本 |
| LLM 成本超阈 | 日 token 成本 > 预算 80% | 邮件 | 手动调低阈值 |
| 队列堆积 | consumer lag > 5k 或持续增长 | IM | 停掉 worker 消费 |
| DLQ 增长 | dlq 总量 > 0 且上升 | IM | 投一条 poison message |

### 3.3 runbook（五类常见故障，每类一页：现象→定位→处置→升级）

```
1 解析失败率升高   → 看 parse-worker 日志/trace 步骤耗时 → 常见：LibreOffice 挂/OCR OOM → 重启 worker/降 dpi
2 LLM 超时/熔断    → 看网关熔断状态 + provider 状态页 → 自动降级仅规则 → 恢复后补跑语义审查任务
3 队列堆积         → kafka-exporter lag → 扩 worker（--scale）→ 检查是否有 poison message 堵分区
4 DB 慢/连接池耗尽 → pg_stat_statements Top → statement_timeout 兜底 → 临时调大 pool 或杀慢查询
5 磁盘满           → MinIO/PG/Kafka 日志分区 → 清 Kafka 旧段/扩容 → 归档任务加速
```

### 3.4 备份与恢复

```bash
# 每日定时（cron 容器）
pg_dump -Fc $DATABASE_URL > backups/pg_$(date +%F).dump      # 保留 14 天
mc mirror minio/contracts backups/minio_contracts/            # 对象存储镜像
# 恢复演练（M8 验收项，实跑记录 RTO）
pg_restore -d $DATABASE_URL --clean backups/pg_latest.dump    # 目标 < 30min
```

## 4. 生产复杂性应对（M8 核心章）

| 真实情况 | 处置 |
|---|---|
| 过度埋点拖慢系统 | 采样 10% + 错误全采；埋点开销设预算（<3% CPU） |
| 指标基数爆炸 | 标签白名单（endpoint/model/status/stage）；code review 拦截高基数标签 |
| 敏感数据进日志/trace | GenAI 内容采集默认关；日志脱敏中间件（主体名/金额掩码白名单）；gitleaks 扫描 |
| 告警疲劳（狼来了） | 每条告警必须可行动（对应 runbook 条目）；阈值宁松勿紧，逐步收紧 |
| 备份"看起来有"但从没恢复过 | 恢复演练是验收硬项，RTO/RPO 实测数字落文档 |
| 灰度切流后新旧版本行为不一致 | 事件契约向后兼容（M6 已建）；DB 迁移 expand-contract 保证新旧代码共存 |
| trace 采样漏掉关键慢请求 | 慢请求（P95 之上）强制采样（tail-sampling Collector 规则） |
| 无人看文档化的 SLO | 错误预算纪律写进 README；每周回顾烧预算率 |

## 5. 测试计划

- 链路验证：发起一次真实审查 → Tempo 中能看到完整 trace（API→parse→extract→rules→llm→approve），每步耗时与 token 齐全。
- 告警演练：5 条告警各触发一次，记录触达时延（目标 1 分钟内）。
- 备份恢复：真跑恢复，记录 RTO/RPO。
- 灰度演练：双实例切流 → 回滚 → 验证服务连续。

## 7. 风险与回滚

| 风险 | 缓解 / 回滚 |
|---|---|
| 可观测栈本身吃光 32G 内存 | 组件按需起（Tempo/Loki 保留期 3 天）；Langfuse 可后置 |
| OTel SDK 版本 API 变动（gen_ai.system 改名等） | 版本锁死 + 语义约定版本记入 ADR |
| 告警阈值拍脑袋 | 先保守值跑两周，按真实分布调；每条告警关联 runbook |
| 回滚后 DB schema 不兼容 | 迁移永远 expand-contract：新版本只加不改，回滚旧代码可跑 |
