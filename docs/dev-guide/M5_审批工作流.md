# M5 审批工作流与权限（并发正确性）—— 开发指引与验收文档

> 周期 W9–W10 ｜ 主轨 A ｜ 对应架构阶段 C4 ｜ **本项目技术核心之二**
> 一句话目标：**AI 的结论能真正进入审批流，且多人并发不出错、跨天不卡死、全程可审计。**

---

## 1. 目标与范围

**做**：手写状态机（转移表数据化）、长流程时间维度（超时催办/驳回重提/撤回）、approval_records append-only、乐观锁、幂等键、事务边界、RBAC 四角色、审计表 DB 层防篡改、审批操作台前端。

**不做**：会签/或签/多分支（触发条件见架构文档演进路径——那时该上 BPM Flowable）、多租户、SSO 对接。

## 2. 技术选型详述

### 2.1 手写状态机 vs BPM（ADR-0003）

- 手写：转移表数据化（YAML）+ guard 函数 + 转移事务，透明可讲、与本项目流程复杂度匹配。
- Flowable/Activiti 不选：Python 项目 + 单链审批，BPM 的 90% 能力闲置；但它是 Java 岗位知识点，**架构文档留了演进路径**（流程复杂到需要会签/并行网关时迁）。

### 2.2 并发正确性三件套（本里程碑的灵魂）

| 机制 | 解决什么 | 原理 |
|---|---|---|
| **乐观锁（version 字段）** | 多人同时审批同一合同 → 丢失更新 | `UPDATE ... SET state=?, version=version+1 WHERE id=? AND version=?`，影响行数=0 → 409。为什么不用悲观锁：审批冲突率极低（通常单人操作），悲观锁（SELECT FOR UPDATE）持锁时间长、死锁风险高，收益不成比例 |
| **幂等键（Idempotency-Key）** | 网络重试/双击 → 重复提交重复扣审 | 唯一索引 `(endpoint, idempotency_key)`；重复请求返回首次结果 |
| **单事务边界** | 改状态成功但写记录失败 → 状态与审计不一致 | 「改状态 + version+1 + 写 approval_record + 写 audit_event」一个 DB 事务 |

### 2.3 长流程时间维度（乐观锁管不到的部分）

乐观锁解决"同一瞬间的并发"，但审批是**跨天、有中间态**的长流程，必须补三件事：
1. **超时催办**：`pending/reviewing` 超过 N 天 → arq 定时任务扫描 → 写催办事件（通知渠道 M6 接 Kafka notify，M5 先落 `reminders` 表）+ 可配置自动退回；
2. **驳回重提重入**：`rejected → draft → pending` 是**主链路**不是异常路径；重入后旧 approval_records **不可覆盖（append-only）**，版本历史完整保留；
3. **撤回**：`withdrawn` 与 `rejected` 语义区分——撤回是提交方主动取消（无责任方），驳回是审批方否决（带意见）。

### 2.4 RBAC 四角色（资源级校验）

`applicant`（提交人）/ `legal_reviewer`（法务初审）/ `legal_lead`（复核）/ `admin`。**资源级**：legal_reviewer 只能审批分派给自己的合同，不是"能调这个接口就行"。JWT claim 带角色，业务层二次校验（不信任网关透传）。

### 2.5 审计防篡改

`audit_events` append-only：应用层只 INSERT；**DB 层兜底**——`REVOKE UPDATE, DELETE ON audit_events FROM app_user`；应用连接用受限账号，防代码 bug 或 SQL 注入越权改历史。

## 3. 详细设计（伪代码级）

### 3.1 数据模型

```sql
CREATE TABLE approvals (            -- 审批单（可重入：一次提交一轮）
    id            UUID PRIMARY KEY,
    contract_id   UUID REFERENCES contracts(id),
    report_id     UUID REFERENCES review_reports(id),   -- 锁定审批时的报告快照
    state         TEXT NOT NULL DEFAULT 'draft',        -- draft/pending/reviewing/
                  -- approved/rejected/withdrawn
    version       INT NOT NULL DEFAULT 0,               -- 乐观锁
    submitted_by  UUID REFERENCES users(id),
    timeout_deadline TIMESTAMPTZ,                       -- 超时催办依据
    created_at TIMESTAMPTZ DEFAULT now(),
    updated_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE approval_records (     -- 每次转移一条，append-only
    id UUID PRIMARY KEY,
    approval_id UUID REFERENCES approvals(id),
    action TEXT NOT NULL,           -- submit/start_review/approve/reject/withdraw/remind
    actor_id UUID REFERENCES users(id), actor_role TEXT,
    comment TEXT,
    from_state TEXT, to_state TEXT, old_version INT, new_version INT,
    created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE idempotency_keys (
    endpoint TEXT, idem_key TEXT, response_body JSONB,
    created_at TIMESTAMPTZ,
    PRIMARY KEY (endpoint, idem_key)                -- 唯一索引防重
);

CREATE TABLE audit_events (         -- DB 层 REVOKE UPDATE/DELETE
    id BIGSERIAL PRIMARY KEY, trace_id TEXT, actor_id UUID,
    event_type TEXT, payload JSONB, created_at TIMESTAMPTZ DEFAULT now()
);
```

### 3.2 状态机（转移表数据化）

```yaml
# workflow/transitions.yaml —— 加流程只改配置不改代码
transitions:
  - { from: draft,     action: submit,      to: pending,   roles: [applicant],
      guard: "report_exists AND no_open_blocker_findings_or_accepted" }
  - { from: pending,   action: start_review,to: reviewing, roles: [legal_reviewer] }
  - { from: reviewing, action: approve,     to: approved,  roles: [legal_lead],
      guard: "all_blocker_findings_resolved" }
  - { from: reviewing, action: reject,      to: rejected,  roles: [legal_reviewer, legal_lead],
      require: comment }
  - { from: pending,   action: reject,      to: rejected,  roles: [legal_reviewer], require: comment }
  - { from: pending,   action: withdraw,    to: withdrawn, roles: [applicant] }
  - { from: reviewing, action: withdraw,    to: withdrawn, roles: [applicant, legal_lead] }
  - { from: rejected,  action: revise,      to: draft,     roles: [applicant] }   # 重入主链路
  - { from: withdrawn, action: revise,      to: draft,     roles: [applicant] }
```

```python
class StateMachine:
    def __init__(self, table=load_yaml("transitions.yaml")): self.table = table

    def transition(self, approval, action, actor) -> Transition:
        t = self.table.find(from_state=approval.state, action=action) \
            or raise Problem(422, "illegal transition",
                    detail=f"{approval.state} --{action}--> 不存在")     # 非法转移：422+记录尝试
        check(t.actor_has_role(actor))            # 角色不符 → 403
        check(evaluate_guard(t.guard, approval))  # guard 不过 → 422（如 blocker 未处理）
        return t
```

### 3.3 转移事务（乐观锁 + 幂等 + 审计一体化）

```python
async def apply_transition(approval_id, action, actor, comment, idem_key):
    # ① 幂等检查：同 key 直接返回首次结果
    if (prev := await idem_repo.find(endpoint, idem_key)): return prev.response

    async with db.transaction():   # ② 单事务：要么全成要么全败
        a = await approval_repo.get_for_update_lockless(approval_id)  # 普通 SELECT（乐观锁思路）
        t = state_machine.transition(a, action, actor)                 # 422/403 检查

        rowcount = await approval_repo.conditional_update(
            where="id = :id AND version = :v AND state = :from",
            values={state: t.to, version: a.version + 1, timeout_deadline: now()+N_days})
        if rowcount == 0:
            raise Problem(409, "version conflict",
                detail="合同状态已被他人更新，请刷新后重试")            # 乐观锁冲突 → 409

        await record_repo.insert(approval_id, action, actor, comment,
                                 from_state=a.state, to_state=t.to,
                                 old_version=a.version, new_version=a.version+1)
        await audit_repo.insert(trace_id, actor.id, f"approval.{action}",
                                {"approval_id":..., "to": t.to})

    resp = {"state": t.to, "version": a.version + 1}
    await idem_repo.save(endpoint, idem_key, resp)     # ③ 幂等结果落库（事务外，失败可容忍）
    await tasks.enqueue("remind_or_notify", approval_id)  # M6 换 Kafka notify
    return resp
```

### 3.4 超时催办（定时任务）

```python
# arq cron：每小时
async def sweep_timeouts(ctx):
    overdue = await approval_repo.where("state IN ('pending','reviewing') AND timeout_deadline < now()")
    for a in overdue:
        await record_repo.insert(a.id, action="remind", actor=SYSTEM)
        await reminder_repo.create(approval_id=a.id, to_role=next_role(a))
        if a.reminded_count >= settings.auto_return_after and settings.auto_return_enabled:
            await apply_transition(a.id, action="auto_return_to_draft", actor=SYSTEM,
                                   comment="超时未处理自动退回")   # 配置开关，默认只催不退
```

### 3.5 API 契约

```
POST /api/v1/approvals                          → 创建审批单（applicant；带 Idempotency-Key）
POST /api/v1/approvals/{id}/actions             → {action, comment}，带 Idempotency-Key
GET  /api/v1/approvals/{id}                     → 当前状态 + version
GET  /api/v1/approvals/{id}/timeline            → 审批轨迹（时间线，供导出审计）
GET  /api/v1/approvals?role=mine&state=pending  → 待办列表（按角色过滤）
```

### 3.6 前端审批操作台

- 待办列表（按角色）→ 审批详情（引用 M4 三栏 + 审批意见区）→ 通过/驳回按钮带**二次确认 + 评论必填（驳回）**。
- 409 冲突处理：toast「状态已变更」→ 自动 refetch → 界面更新到最新状态。

## 4. 生产复杂性应对（M5 核心章）

| 真实情况 | 处置 |
|---|---|
| 20 人同时点"通过" | 乐观锁：恰好 1 成功 19 个 409（自动化测试证明），前端引导刷新 |
| 同一请求网络层重放 | Idempotency-Key 唯一索引，只产生一条记录 |
| 状态机非法跳转（hack 或前端 bug） | 422 + 记录尝试进 audit_events（安全审计素材） |
| 合同卡死在中间态 | 超时催办 cron + 可配置自动退回（§3.4） |
| 驳回重提后历史被冲掉 | approval_records append-only + DB REVOKE；每轮审批关联新 report 快照 |
| 审批人离职/转岗 | M5 先 admin 可改派（record 标 system_action=assign）；组织架构对接留演进 |
| "通过"后发现 AI 审查有漏 | 已 approved 不可逆（审计要求）；出路 = 新版本合同重新走流程——符合法务实际操作 |
| 时钟漂移导致催办误判 | timeout 基准用 DB now()（单源时间），不用应用服务器时钟 |
| 前端缓存旧 version 后提交 | 409 + refetch 即可恢复；不引入服务端 session |

## 7. 风险与回滚

| 风险 | 缓解 / 回滚 |
|---|---|
| 状态机随需求膨胀 | 转移表 YAML 数据化，加流程改配置；复杂到会签 → 上 BPM（演进路径） |
| 乐观锁 version 滥用（所有表都加） | 只加在"有状态有并发写"的 approvals；纯只读表不加 |

| 审计表写放大拖慢审批 | audit 与业务同事务（一致性优先），量大后评估异步化（M6 Kafka audit.events 天然承接） |
