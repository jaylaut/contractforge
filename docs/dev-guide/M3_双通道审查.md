# M3 双通道审查（规则引擎 + LLM 语义）—— 开发指引与验收文档

> 周期 W5–W6 ｜ 主轨 A ｜ **本项目技术核心**
> 一句话目标：**确定性的交给代码，语义的交给模型；每条风险可判定、可定位、可复核。**

---

## 1. 目标与范围

**做**：Rule 协议 + 首批 8 条规则（YAML 配置化）、规则"两分类"（纯字符串 vs 依赖抽取）、LLM 按条款分组并发语义审查、Finding 输出契约、聚合去重、风险分级、降级路径（关 LLM 仍可用）、规则说明文档（法务人话版）。

**不做**：法务裁决（AI 只提示，裁决权在人——合规红线）、法律知识图谱、跨合同比对（M8 后演进）。

---

## 2. 技术选型详述

### 2.1 规则引擎：手写 + 协议化 + YAML 配置

- **为什么手写**：规则总量 ≤ 20 条，引入 Drools 类/规则引擎框架是过度设计；手写 `Rule` 协议（`code / severity / evaluate(ctx) -> list[Finding]`）透明、可测、可讲。
- **配置化**：阈值、严重级、启停放 YAML（`rules.yaml`），调规则不改代码——真实法务场景里阈值（如违约金上限 30%）随公司政策变化。
- **⚠️ 伪确定性点破（本里程碑最重要的设计决策）**：
  - **纯字符串规则**：金额大小写一致、金额合计一致——用正则/解析**直接在原文**把所有金额数字（含汉字大写）扒出来比对，**与 LLM 完全解耦**，这才是真确定性；
  - **依赖抽取结果的规则**：违约金比例、日期先后——输入来自 M2 的 LLM 抽取，**LLM 抽错则规则"自洽地"校验错**，是伪确定性；
  - **落地**：后者在 Finding 里必须标 `source_dependency=llm`，不得与确定性规则混为一谈；两类规则的召回率验收标准不同（前者 100%，后者受限于抽取准确率）。

### 2.2 LLM 语义审查：按条款分组 + 信号量限流

- **为什么不整篇硬塞**：① 长合同超上下文；② 注意力稀释——一次只喂相关条款，召回质量显著更高；③ 条款级调用可并行、可重试、可定位（Finding 天然带 clause_id）。
- **并发控制**：`asyncio.Semaphore(N)`（N 按 provider 配额定，如 3）+ 网关熔断兜底；每条款一次调用，失败单条重试不影响整体。

### 2.3 prompt 工程

- 文件化版本管理：`prompts/review_v2.md`，含角色设定、审查维度清单（违约责任不对等/争议条款模糊/显失公平/格式条款风险）、输出 json_schema、few-shot 示例。
- temperature=0 + 结构化输出 + 双跑一致性抽样（抽样 5% 双跑，不一致率 > 10% → prompt 需要改）。

## 3. 详细设计（伪代码级）

### 3.1 数据模型

```sql
CREATE TABLE findings (
    id           UUID PRIMARY KEY,
    contract_id  UUID REFERENCES contracts(id),
    report_id    UUID,                        -- M4 引入 report 快照；M3 先用 contract 维度
    source       TEXT NOT NULL CHECK (source IN ('rule','llm')),
    rule_id      TEXT,                        -- rule 来源必填；llm 可空
    source_dependency TEXT DEFAULT 'none' CHECK (source_dependency IN ('none','llm')),
                    -- 'none'=纯字符串规则（真确定性）；'llm'=依赖抽取结果（伪确定性）
    level        TEXT NOT NULL CHECK (level IN ('blocker','major','minor','info')),
    clause_id    UUID REFERENCES clauses(id),
    quote        TEXT NOT NULL,               -- 原文定位
    basis        TEXT NOT NULL,               -- 判定依据（规则号 / LLM 说理）
    suggestion   TEXT NOT NULL,               -- 修改建议
    llm_meta     JSONB,
    created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_findings_contract ON findings(contract_id, level);
```

### 3.2 Rule 协议与首批 8 条

```python
class RuleContext:
    lines: list[LineItem]         # M1 原文（含坐标）
    clauses: list[Clause]         # 条款树
    fields: dict[str, Field] | None   # M2 抽取结果——纯字符串规则不得使用！

class Rule(Protocol):
    code: str; severity: Level; enabled: bool; dependency: Literal["none","llm"]
    def evaluate(self, ctx: RuleContext) -> list[Finding]: ...

RULES = {
  "AMT_CASE_MATCH":  CaseAmountRule,        # ① 金额大小写一致 —— 纯字符串：正则扒原文
  "AMT_TOTAL_MATCH": TotalAmountRule,       # ② 金额合计一致   —— 纯字符串
  "DATE_VALIDITY":   DateValidityRule,      # ③ 日期合法性与先后 —— llm 依赖（用抽取的 date）
  "CLAUSE_REQUIRED": RequiredClauseRule,    # ④ 必备条款缺失（违约/争议/期限…）—— 纯结构（条款树）
  "PENALTY_CAP":     PenaltyCapRule,        # ⑤ 违约金比例超上限（阈值 YAML：默认 30%）—— llm 依赖
  "DISPUTE_PRESENT": DisputeVenueRule,      # ⑥ 争议解决地缺失 —— 纯结构 + 抽取辅助
  "PLACEHOLDER_LEFT":PlaceholderRule,       # ⑦ 空白占位未填（____、【】、X年X月）—— 纯字符串
  "PARTY_NAME_CONSIST": PartyNameRule,      # ⑧ 主体名称前后不一致 —— 纯字符串（全文统计）
}
# rules.yaml: { AMT_CASE_MATCH: {enabled: true, severity: blocker}, PENALTY_CAP: {cap: 0.30} }
```

### 3.3 纯字符串规则示例（真确定性）

```python
class CaseAmountRule:
    code, severity, dependency = "AMT_CASE_MATCH", "blocker", "none"

    CN_NUM = {"零":0,"壹":1,...,"拾":10,"佰":100,"仟":1000,"万":1e4,"亿":1e8}
    AMT_DIGIT = re.compile(r"[¥￥RMB]?[\d,，]+(?:\.\d+)?\s*元")
    AMT_CN    = re.compile(r"[人民币]*[壹贰叁肆伍陆柒捌玖拾佰仟万亿]+(?:元|圆)整?")

    def evaluate(self, ctx):
        findings = []
        # 直接连 LineItem 原文工作，与 LLM 无关
        digit_amts = {locate(ctx.lines, m): to_decimal(m) for m in self.AMT_DIGIT.finditer(full_text)}
        cn_amts    = {locate(ctx.lines, m): cn_to_decimal(m) for m in self.AMT_CN.finditer(full_text)}
        # 大写金额必须在数字金额中有等值对（同一句子级上下文内）
        for pos, cn in cn_amts.items():
            if not any(abs(d - cn) < Decimal("0.01") for d in nearby(digit_amts, pos)):
                findings.append(Finding(level="blocker", clause_id=clause_at(pos),
                    quote=ctx.lines[pos].text, basis="AMT_CASE_MATCH",
                    suggestion=f"大写金额 {cn} 与相邻数字金额不一致，请核对"))
        return findings
```

### 3.4 LLM 语义审查

```python
async def llm_review(clauses, fields):
    sem = asyncio.Semaphore(settings.llm_review_concurrency)   # 默认 3
    async def one(clause):
        async with sem:
            prompt = load_prompt("review_v2", clause=clause.text)
            resp = await llm.chat(messages=prompt, temperature=0,
                        response_format=json_schema(FindingsSchema))
            return validate_findings(resp, clause)    # 出站校验 + clause_id 回填 + quote 校验
    tasks = [one(c) for c in clauses if needs_semantic_review(c)]  # 跳过标题/前言
    return flatten(await gather(*tasks))

def validate_findings(resp, clause) -> list[Finding]:
    out = []
    for f in resp.findings:
        if not fuzzy_locate(f.quote, clause, threshold=0.9):
            f.level = "minor"; f.basis += "（原文定位为模糊匹配，请人工确认）"  # 定位不可信 → 降级提示
        out.append(f)
    return out
```

### 3.5 聚合去重与分级

```python
def aggregate(rule_findings, llm_findings) -> list[Finding]:
    merged = {}
    for f in rule_findings:                       # 规则优先：同 clause 同问题，规则结论覆盖 LLM
        merged[(f.clause_id, f.basis_key)] = f
    for f in llm_findings:
        key = (f.clause_id, f.basis_key)
        if key in merged: continue                # 确定性优先，丢弃重复 LLM 判断
        if overlaps_location(f, merged.values(), tolerance=1_clause):
            merged[key].supplement(f)             # 同位置 → 合并补充 LLM 说理
        else: merged[key] = f
    return sort_by_severity(merged.values())      # blocker > major > minor > info
```

分级语义（给审批用的业务约定）：`blocker` = 审批必须处理才可放行；`major` = 应处理；`minor`/`info` = 提示。

## 4. 生产复杂性应对（M3 核心章）

| 真实情况 | 处置 |
|---|---|
| LLM 审查结果不稳定 | prompt 版本固化 + temperature 0 + 结构化输出 + 双跑一致性抽样；仍抖的规则转确定性规则 |
| LLM 服务挂掉/超时 | 网关熔断 → 纯规则路径兜底，报告明确标注"语义审查未执行"（诚实降级优于静默缺失） |
| 伪确定性污染 | 两类规则强标注 `source_dependency`；依赖类规则的 Finding 前端显示"基于 AI 抽取，请核对原文" |
| 规则误报骚扰法务 | 验收误报 ≤5%；规则 YAML 可按公司政策调阈值/停用；每条规则附人话说明 |
| 同一问题规则和 LLM 都报 | 聚合去重（§3.5），确定性优先，不让法务看到两条重复 |
| 条款超长（一页一条） | 单条款超 token → 按句切分多次调用再归并 |
| 汉字大写金额的变体（"拾万零伍佰"） | cn_to_decimal 用穷举单测覆盖（hypothesis 属性测试：cn↔digit 往返一致） |
| 合同没写争议条款但业务上不需要 | 分级为 major 而非 blocker，法务可一键"接受"——AI 提示、人来裁决 |

## 5. 测试计划

- **规则单测：表驱动 100% 覆盖**——每条规则 ≥ 正例 3 / 反例 3 / 边界 2；构造样本必须全中（召回 100% 是验收门禁）。
- hypothesis 属性测试：金额（任意 Decimal ↔ 汉字大写往返）、日期（闰年/月末边界）。
- LLM 评测：golden set 20 份人工复核 → 可用率 ≥ 80%。
- 降级演练：断 LLM 配置跑全链路，规则结果完整、报告标注降级。
- 端到端 P95：30 页合同 ≤ 90s。
