# ContractForge 项目架构文档

> **项目定位**：在已完成的 RAG 平台（`rag-from-llm-ai`）与 Agent 平台（`agentforge`）之上，第三个项目——从「知识问答」走向「业务闭环」，做一个**真实业务场景、企业级、全栈**的智能合同审查与审批协作系统。
> **双重目标**：① 把 AI 能力落到一个真实业务，理解「企业级 AI 应用」的完整工程闭环；② 形成与「Java 后端 + AI」目标岗位强对口的硬材料（审批流、可追溯、规则引擎、pgvector、全栈）。
> **技术原则**：延续前两个项目的「底层手写」，不引入 LangChain/LlamaIndex；复用 agentforge 已验证的 LLM 网关与结构化输出方案。

## 〇、这份文档怎么读

延续前两个项目（RAG 的 P 系列、Agent 的 A 系列）的方法论，本项目阶段记为 **C 系列**（C0~C5）：

1. **学习主线**：每个模块不仅写「用什么」，更写「为什么、原理是什么、怎么验证学会了」。
2. **工程主线**：每个技术选型都给出量化依据与 trade-off（为什么选它、为什么不选别的）。
3. **业务主线**：本项目新增——每个设计都要回答「这个能力在企业里真的会被买单吗」。

> **一句话定位**：不是「我搭了个能审合同的 AI demo」，而是「我以企业级标准，把 LLM 能力落进了一个真实业务——合同审查，并解决了『AI 结果如何可靠进入审批流、可追溯、可审计』这个企业真正买单的问题」。

## 一、为什么是「合同审查」这个方向（决策 C0）

### 1.1 与前两个项目形成递进，而非重复

| 项目 | 核心能力 | 本质 | 阶段 |
|---|---|---|---|
| RAG 平台 | 检索增强生成 | 知识问答 | P 系列 |
| Agent 平台 | 自主规划 + 工具调用 | 任务执行 | A 系列 |
| **本项目** | 文档审查 + 审批协作 | **业务闭环** | C 系列 |

### 1.2 三个选型理由

1. **真实刚需**：合同审查、法务尽调是企业里付费意愿最强的 AI 场景之一，也是「Java 后端 + AI」岗位 JD 里反复出现的真实业务。
2. **契合 Java 背景**：本项目 60% 的价值在「AI 审查结果如何可靠进入审批流、可追溯、可审计」——这是工程能力，不是 AI 能力。
3. **体现「确定性 + AI」结合**：合同审查不能只靠 LLM（会幻觉），必须「规则引擎（确定性）+ LLM（语义理解）」双通道。

### 2.2 一次合同审查的完整旅程

```
上传合同(PDF/Word/扫描件)
  → 文档解析（格式探测 → pdfplumber/docx/PaddleOCR → 分条款结构化）[C0]
  → 要素抽取（LLM Function Calling → 结构化 JSON）             [C1]
  → 双通道审查：                                              [C2]
      规则引擎（确定性校验：金额数字、日期格式、关键条款缺失）
      + LLM 语义审查（违约责任、争议条款、模糊表述）
  → 风险点聚合（每条风险：等级 + 原文定位 + 依据 + 修改建议）
  → 生成审查报告（结构化，含高亮标注）                         [C3]
  → 提交审批流（状态：草稿 → 待审 → 复核 → 通过/驳回）          [C4]
  → 全程 trace_id 贯穿，每次操作落库可追溯
```

## 三、并发、异步、分布式设计（架构核心章节）

> 本项目不是「百万 QPS」系统，但**并发、异步、分布式三个维度恰恰是「Java 后端 + AI」岗位最看重的架构能力**。关键不是「堆多少分布式组件」，而是**准确分析合同审查场景的负载特征，再据此做实事求是的架构设计**——这正是资深架构师和「会写 CRUD」的区别。

### 3.1 先分析负载特征（一切设计的起点）

合同审查场景的负载，和「秒杀/高并发」完全不同，必须看清它的真实特征：

| 特征 | 合同审查场景 | 对架构的启示 |
|---|---|---|
| **请求量** | 低频（一天几百到几千份合同），非高 QPS | 不需要「百万 QPS」的并发优化，但要有**并发正确性** |
| **单请求耗时长** | 一次审查 = 解析 + LLM 抽取 + LLM 审查，可能 30s~几分钟 | **必须异步**，不能阻塞 API |
| **CPU/IO 混合** | 解析是 CPU 密集，LLM 调用是 IO 密集（远程 API） | 要区分两类任务的并发模型 |
| **有状态** | 审批流有状态、有并发修改（多人同时审批） | **必须处理并发一致性**（乐观锁） |
| **数据敏感** | 合同是敏感数据 | 影响分布式部署（数据不出域、脱敏） |

> **一句话结论**：这个系统**不需要「高并发」，但需要「并发正确性 + 异步任务 + 分布式可扩展」**——这比盲目上高并发更体现架构功力。

### 3.2 并发设计（并发正确性，而非并发量）

**核心矛盾**：审批流是「有状态 + 多人并发修改」，这是并发 bug 的高发区。

| 并发场景 | 问题 | 设计 |
|---|---|---|
| 多人同时审批同一份合同 | 后写覆盖先写（丢失更新） | **乐观锁**：审批记录带 `version` 字段，更新时 `WHERE version = ?`，冲突则提示重读 |
| 同一合同重复提交审查 | 重复扣费、重复生成 | **幂等设计**：提交时带 `idempotency_key`，唯一索引防重 |
| 审查任务被重复触发 | 任务重复执行 | 任务状态机（pending → running → done），抢占时用原子更新防重 |
| 读多写少（合同列表/报告查看） | 频繁查库 | 读场景可加缓存（Redis），写场景走事务 |

**关键设计**：
- **乐观锁（version 字段）**：审批流并发控制的头号手段，对应你 Java 背景熟悉的「乐观锁/悲观锁」权衡。
- **幂等键（idempotency_key）**：所有「提交」类操作幂等，防重放。
- **数据库事务**：一次「审批通过」操作 = 更新状态 + 写审批记录 + 更新版本，必须在一个事务里（ACID）。

> **面试金句**：「这个系统不是高并发，但审批流是『有状态 + 多人并发修改』，最容易出并发 bug。我用乐观锁解决丢失更新、幂等键防重复提交，把并发正确性做扎实——这比盲目堆高并发更体现架构能力。」

### 3.3 异步设计（长任务不阻塞）

**核心矛盾**：一次合同审查 30s~几分钟，绝不能同步阻塞 API 响应。

| 异步场景 | 设计 |
|---|---|
| 文档解析（CPU 密集，长耗时） | 提交后立即返回 `task_id`，解析进**任务队列**后台执行 |
| LLM 抽取 + 审查（IO 密集） | 同样进队列，异步执行 |
| 批量审查（一批合同） | 拆成多个子任务并行入队 |
| 进度通知 | 前端轮询 `task_id` 状态，或用 SSE/WebSocket 推送进度 |

**异步架构分层**：

```
同步层（FastAPI）          异步层（arq 任务队列）
─────────────────          ─────────────────────────
POST /contracts           → 入队 parse_task
  立即返回 {task_id}         worker: 解析 → 分条款
GET /contracts/{id}/status → 查任务状态
                           → 入队 extract_task
                              worker: LLM 要素抽取
                           → 入队 review_task
                              worker: 规则+LLM 双通道审查
                           → 状态回调：更新合同状态
```

**关键设计**：
- **任务队列（arq + Redis）**：长任务全部异步，API 只负责「入队 + 查状态」。
- **任务状态机**：`pending → running → success / failed`，支持重试（解析失败重试、LLM 失败退避重试）。
- **幂等重试**：任务重试必须幂等（重复执行不会产生重复数据）。
- **超时与熔断**：LLM 调用复用 agentforge 网关的超时/降级。

> **为什么是「异步」而不是「多线程」**：合同审查是长任务，用户能接受「提交后等几分钟」，异步任务队列比多线程更能保证**可靠性**（持久化、重试、不丢任务）。这也是「企业级」和「demo」的区别。

### 3.4 分布式设计（可扩展，而非强行拆分）

**核心原则**：**先单体 + 明确的演进路径，不为分布式而分布式。** 但架构要「为分布式做好准备」。

| 维度 | 当前（单体起步） | 分布式演进路径 |
|---|---|---|
| **无状态服务** | FastAPI 无状态（状态都在 DB/Redis） | 天然可水平扩展：多个 API 实例 + 负载均衡 |
| **任务 worker** | 单 worker 进程 | 多 worker 进程（arq 支持多 worker 消费同一队列） |
| **数据库** | 单机 PostgreSQL + pgvector | 主从读写分离 → 分库（按租户/合同） |
| **缓存** | 单机 Redis | Redis Cluster |
| **会话** | JWT 无状态（不依赖服务器 session） | 天然支持多实例，无需粘性会话 |

**关键设计**：
- **服务无状态化**：API 层不保存任何会话/业务状态，状态全部外置（DB/Redis），这是水平扩展的前提。
- **JWT 认证**：无状态认证，天然支持多实例，不需要服务器 session 共享。
- **任务队列解耦**：解析/审查/通知通过队列解耦，worker 可独立扩容。
- **明确「何时才真正需要分布式」**：单机 PG 能扛几千份合同/天，量级未到就不强行分库分表——这是「实事求是」的架构判断。

> **面试金句**：「我不为分布式而分布式。当前量级单体 + 无状态 + 异步队列就能稳定运行，但我把服务设计成无状态、状态外置、队列解耦，量级上来时能平滑地水平扩展 API 实例和 worker，数据库走主从 → 分库的演进路径。这是『架构要能演进』的正确做法。」

### 3.5 三个维度的关系（一张图总结）

```
       并发（正确性）          异步（不阻塞）          分布式（可扩展）
   ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
   │ 乐观锁防丢失更新    │  │ 长任务进队列       │  │ 无状态服务可水平扩  │
   │ 幂等键防重复提交    │  │ 任务状态机+重试     │  │ JWT 无状态认证     │
   │ 事务保证一致性      │  │ 超时熔断           │  │ 队列解耦 worker 扩容│
   └──────────────────┘  └──────────────────┘  └──────────────────┘
         ↓ 有状态改动        ↓ 长耗时操作           ↓ 量级增长
      审批流/提交操作      解析/LLM审查/批量      水平扩展时机
```

**一句话总结三个维度**：
> **并发**解决「审批流多人同时改不出错」；**异步**解决「长任务不阻塞用户」；**分布式**解决「量级增长时能平滑扩展」。三者分别对应「正确性、体验、可扩展」，缺一不可，但都要**贴合实际负载、不过度设计**。

### 3.6 服务间关系与交互协议（谁调用谁、怎么调用）

> 前面的分层架构图是「按层次看」，这一节是「按服务看」——明确每个服务的**职责边界、依赖关系、调用方向、同步还是异步**。这是分布式架构里最容易被忽略、但面试最爱追问的一层。

#### 3.6.1 服务清单与职责边界（单一职责）

| 服务 | 类型 | 状态 | 职责（只做这一件事） | 不做什么 |
|---|---|---|---|---|
| **Gateway（Nginx）** | 接入 | 无状态 | 反向代理、负载均衡、限流、SSL 终结 | 不处理业务逻辑 |
| **API（FastAPI）** | 业务 | 无状态 | 接收请求、鉴权、参数校验、入队/查询、同步短操作 | 不做长耗时任务、不存业务状态 |
| **Worker（审查流水线）** | 任务 | 无状态 | 消费队列，执行解析→抽取→审查，回写结果 | 不直接面对前端、不处理同步请求 |
| **LLM 网关（复用 agentforge）** | 基础设施 | 无状态 | 统一 LLM 调用：重试/降级/计费/结构化输出 | 不做业务编排 |
| **规则引擎** | 业务组件 | 无状态 | 确定性校验（金额/日期/条款缺失） | 不做语义判断（交给 LLM） |
| **PostgreSQL + pgvector** | 数据 | **有状态** | 唯一事实源：合同/要素/风险/审批流/向量 | 不存大文件 |
| **Redis** | 数据 | **有状态** | 缓存 + 分布式锁 + 队列后端 | 不做持久事实源 |
| **Kafka** | 消息 | **有状态** | 异步解耦、削峰、事件流 | 不做业务计算 |
| **对象存储（MinIO）** | 数据 | **有状态** | 合同原文 PDF/Word 文件 | 不存结构化数据 |

**关键点：只有数据层（PG/Redis/Kafka/对象存储）是有状态的，其余全部无状态。** 无状态服务是水平扩展的前提，有状态服务是「事实源」和「扩展难点」。

#### 3.6.3 调用类型分类（同步 vs 异步）

| 调用关系 | 类型 | 协议/通道 | 说明 |
|---|---|---|---|
| 前端 → Gateway → API | 同步 | HTTP/HTTPS | 请求-响应，短连接 |
| API → PostgreSQL | 同步 | SQL (asyncpg) | 短操作直接读写事实源 |
| API → Redis | 同步 | Redis 协议 | 缓存读写、分布式锁 |
| API → Kafka（发消息） | **异步** | Kafka Producer | 长任务入队，立即返回 task_id |
| Kafka → Worker（消费） | **异步** | Kafka Consumer | 流水线解耦，worker 拉取处理 |
| Worker → LLM 网关 | 同步（长） | HTTP | 长耗时 LLM 调用，有超时/重试 |
| Worker → PostgreSQL | 同步 | SQL | 回写审查结果 |
| Worker → 对象存储 | 同步 | S3 协议 | 读写合同原文 |
| API → 前端（进度推送） | 异步 | SSE / 轮询 | 任务进度通知 |

#### 3.6.4 关键调用链（一次审查请求的完整路径）

```
① 用户上传合同
   前端 → Gateway → API
   API 鉴权(JWT) → 校验 → 文件存 MinIO → 写 DB(合同记录, 状态=草稿)
   API 发 Kafka「parse_task」→ 立即返回 {task_id}   ← 同步段结束，<100ms

② 异步流水线（Worker 消费）
   Kafka → Worker:
     parse(读 MinIO 原文 → pdfplumber/docx 解析 → 分条款)
       → 发 Kafka「extract_task」
     extract(LLM 网关抽取要素 → 结构化 JSON)
       → 发 Kafka「review_task」
     review(规则引擎确定性校验 + LLM 语义审查 → 风险点聚合)
       → 写 DB(风险点 + 审查报告) → 更新合同状态

③ 审批流（同步段）
   法务 → 前端 → API: 拉取审查报告(读 DB) → 提交审批(乐观锁更新版本)
   → 写审批记录 → 发 Kafka「notify_event」

④ 通知（异步段）
   Kafka → 通知服务消费「notify_event」→ 推送给相关角色
```

**这条链里体现的关键设计**：
- **同步段很短**（上传、查询、审批操作都是 <100ms），**长耗时全部走异步**（解析/LLM 审查进队列）。
- **Kafka 是「解耦点」**：API 和 Worker 之间、Worker 各步骤之间，全部通过 Kafka 解耦，谁挂了不影响别人。
- **PostgreSQL 是「唯一事实源」**：所有状态变化最终都落回 DB，Redis/Kafka 只是「加速层/缓冲层」，不是事实源。

#### 3.6.5 交互协议清单（汇总）

| 协议 | 用在谁之间 | 为什么 |
|---|---|---|
| HTTP/HTTPS (REST) | 前端 ↔ API、API ↔ 外部服务 | 通用、生态成熟 |
| SSE | API → 前端 | 进度推送（单向流） |
| SQL | API/Worker ↔ PostgreSQL | 结构化数据的唯一通道 |
| Redis 协议 | API ↔ Redis | 缓存/锁，低延迟 |
| Kafka 协议 | API/Worker/通知服务 之间 | 异步解耦、削峰、事件流 |
| S3 协议 | Worker ↔ MinIO | 大文件读写 |

## 四、核心技术选型（每个决策都有对比与理由）

### C-D1 文档解析：pdfplumber + python-docx + PaddleOCR

> **本节是全系统设计的承重墙，必须单独立一节展开。** 前面所有章节的验收指标（高亮定位、evidence 溯源、规则定位）都建立在「能拿到文字与坐标」这个假设上。真实合同一半以上会打破这个假设——这一节回答「输入到底是什么、打不开时怎么办」。

**先摆事实：真实合同语料长什么样。** 这是设计的起点，不是风险里带一句的边角料。

| 语料形态 | 真实占比 | 文本层 | 坐标 | 处理路径 |
|---|---|---|---|---|
| 文本型 PDF（Word/系统导出） | 中 | 有 | 有 | pdfplumber 直接提取 |
| **扫描型 PDF（盖章件/传真件）** | **高** | **无** | 无 | **PaddleOCR** |
| 图片（拍照/截图） | 中 | 无 | 无 | PaddleOCR |
| 加密 / 权限受限 PDF | 中 | 有但锁 | 不可读 | 探测后阻断，提示用户解密 |
| DOCX | 高 | 有 | **无页坐标** | python-docx + 转 PDF 对齐坐标 |
| 旧 `.doc` / `.wps` | 中 | — | — | 需转换（LibreOffice/LibreOffice headless） |

**四个选型结论（每个都回答了「真实场景里会怎样」）：**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **pdfplumber + python-docx** | 纯 CPU、带坐标（做「风险点原文定位」）、无需 GPU | 表格/复杂版式解析有难度；**只覆盖「有文本层」的输入** | 文本层入口，选它 |
| **PaddleOCR（本地）** | 覆盖扫描件/图片（真实占比最高的一类）；**数据不出域**（合同敏感，这是硬约束） | 需要 onnx/paddle 运行时，CPU 推理慢、坐标精度低于原生文本层 | **主线必选**，不是演进路径 |
| pypdf | 轻量 | 提取质量一般、无坐标 | 不选 |
| 云服务（百度/腾讯 OCR） | 质量高 | 要付费、**数据出域**（合同敏感，合规红线） | 不选（合规） |

> **关键点 1（坐标）**：pdfplumber 提取文字的**页面坐标**，是「审查报告高亮标注原文位置」的基础——本项目区别于「只输出文本」的关键体验点。
> **关键点 2（OCR 主线化）**：扫描件/图片是真实法务场景里占比最高的一类语料，**所以 OCR 不是「演进路径」，是 C-D1 的主线能力**。这是本版本相对早期方案的关键修正——早期把 OCR 推到「演进路径」，等于主线全程只能处理文本型 PDF，那是不成立的。

**降级矩阵（每种输入，下游怎么办——这是「生产复杂度」的显式落点）：**

| 语料形态 | 解析结果 | 坐标可用 | 前端高亮 | evidence 溯源 | 审查 |
|---|---|---|---|---|---|
| 文本型 PDF | 完整 | ✅ | 精确 | 精确 | 正常 |
| 扫描型/图片（OCR） | 完整但有错字 | ⚠️ 有 bbox、精度略低 | 可用 | 可用（错字容错） | 正常但慢 |
| 加密 PDF | **失败** | ❌ | 不可用 | 不可用 | **阻断，提示用户解密后重传** |
| DOCX | 完整 | ⚠️ 段落级（无页坐标） | 段落级定位 | 段落级 | 正常 |
| 旧 .doc/.wps | 转 PDF 后完整 | 转 PDF 后有 | 转 PDF 后 | 转 PDF 后 | 正常 |

> **这是一张必须有的表**：早期方案里「扫描件降级为整段文本」一句话带过，但没有回答「降级后 M3 审查 / M4 高亮 / M2 溯源到底还能不能用」。这张表就是那个答案——**高亮和溯源在 OCR 路径下仍可用（坐标来自 OCR bbox），只是精度略低；真正阻断的只有「加密 PDF」这一种，明确让用户重传，而不是静默降级。**

**DOCX 无页坐标这个隐蔽坑（必须点破）：** DOCX 是流式（段落+表格），**没有页面坐标**。高亮定位需要坐标，因此 DOCX 解析后必须**转 PDF 取坐标对齐**（LibreOffice headless 转换），或按段落序号降级定位。这是「统一成同一 LineItem 结构」背后必须补齐的一环，否则 DOCX 合同的高亮与溯源就是空中楼阁。

### C-D2 要素抽取：LLM Function Calling + pydantic 校验

- 复用 agentforge 已验证方案：`response_format=json_object` + pydantic 出站校验 + 失败重问。
- 要素 schema：`{甲乙方、金额、币种、起止日期、违约责任、争议解决方式、特殊条款}`。

### C-D3 双通道审查（本项目核心设计）

| 通道 | 作用 | 为什么需要 |
|---|---|---|
| **规则引擎**（确定性） | 金额数字一致性、日期合法性、关键条款缺失、大小写金额一致 | LLM 会幻觉，确定性校验必须由代码保证 |
| **LLM 语义审查**（智能） | 违约责任不对等、争议条款模糊、显失公平表述 | 语义理解是 LLM 强项，规则引擎做不到 |

> **面试金句**：「企业级 AI 审查不能只靠 LLM（会幻觉），我做了『规则引擎 + LLM』双通道——确定性的事交给代码，语义的事交给模型，这才是能上生产的 AI。」
>
> **⚠️ 必须点破的「伪确定性」陷阱（真实复杂度）**：「金额大小写一致 / 金额合计一致」这类规则，**输入本身来自 M2 的 LLM 抽取结果**。如果金额是 LLM 抽出来的，那规则引擎校验的"确定性"其实是**建立在 LLM 结果之上的伪确定性**——LLM 抽错金额，规则就会对着一堆错数"自洽地"校验通过。真正的确定性兜底必须是**不经过 LLM 的字符串级校验**：用正则/解析直接在原文里把所有金额数字（含大小写汉字数字）扒出来比对，这一步与 LLM 完全解耦。**结论：规则引擎要分两类——「纯字符串规则」（真正独立于 LLM）和「依赖抽取结果的规则」（LLM 正确才可靠），后者必须标注，不能和前者混为一谈。**

### C-D4 工作流引擎：手写轻量状态机

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **手写状态机** | 透明、学习价值高、轻量、Java 背景熟悉 | 复杂流程要自己维护 | **选它** |
| Flowable/Activiti | 企业级 BPM | Python 项目、流程简单，杀鸡用牛刀 | 不选（Java 背景加分知识点） |

- 状态机：`草稿 → 待审 → 复核中 → 已通过 / 已驳回`，每步转移记录操作人、时间、意见。
- **⚠️ 长流程的时间维度（真实复杂度，早期漏了）**：审批是**跨天、有中间态**的长流程，不只是"同一瞬间的并发"。必须补三件事：
  1. **状态超时与催办**：合同卡在 `待审`/`复核中` 超过 N 天不处理，要能自动催办/退回，否则合同永远卡死；
  2. **驳回重提的重入**：`已驳回 → 草稿（修改后重新提交）` 是主链路，不是异常路径，状态机要支持循环重入，且重入后旧审批记录不可覆盖（append-only）；
  3. **撤回/作废**：法务发现错误可撤回（`→ withdrawn`），与"驳回"区分语义。
  > 乐观锁解决的是"同一时刻的并发写"，但**长流程的时间语义（超时、重入、撤回）才是审批流真实复杂度的主体**——这也是"手写状态机"最容易漏、而 BPM 引擎天生内置的部分。

### C-D5 数据库：PostgreSQL + pgvector

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **PostgreSQL + pgvector** | 关系数据 + 向量检索一体；纯 CPU 友好；对接 Java 后端规划 | 要起 PG 服务（Docker） | **选它** |
| SQLite（agentforge 用了） | 简单 | 无向量能力、并发弱 | 不选 |
| 独立向量库（Milvus/Qdrant） | 专业 | 多一个服务、运维成本 | 不选（量级用不上） |

> **关键点**：pgvector 是「传统企业 AI 落地」的黄金选择，也是「Java 后端 + AI」岗位最该会的技术。
>
> **⚠️ 必须补齐的地基（早期方案漏了）**：向量检索的真实质量由 **embedding 模型**决定，而不是 pgvector 本身。选 pgvector 只是选了"存向量的地方"，**"向量怎么来的"才是关键**。本项目选定：
> - **嵌入模型：`Qwen3-Embedding-0.6B`**（Apache 2.0，本地推理，避免合同语义数据出域，与 OCR 同理）。0.6B 参数、32K 上下文、最大 1024 维，支持 MRL（Matryoshka，可截断维度省存储）。
> - **重排模型：`Qwen3-Reranker-0.6B`**（同系列同尺寸 cross-encoder）。二阶段检索：embedding 粗召回 top-K → reranker 精排，比纯 embedding 检索通常提升 5–15% 精度。
> - **⚠️ 已知 trade-off（诚实标注，且已拍板）**：0.6B 版的中文检索精度（C-MTEB）**明显弱于 4B/8B 版**。**决策：第一版先用 0.6B 跑通链路（单机 32G CPU 可负担、推理快），把向量检索的工程链路（embedding 入库 → pgvector 索引 → 召回 → 重排 → 喂给 LLM）先验证闭环；中文精度问题留到链路跑通后再用真实合同数据评测**——若相似条款召回质量不达标，升级路径是 `Qwen3-Embedding-4B` + `Qwen3-Reranker-4B`（仍本地、仍同一系列，只换模型权重、重建索引，代码结构不变）。
> - **「相似条款检索」的业务价值**：审查看的是"这条条款有什么风险"，而非"哪份合同条款长得像"。相似条款检索真正的价值是**给 LLM 审查提供参考判例**（"历史上这条条款被怎么改过/判过"），若只是"召回长得像的条款"则价值存疑，有"为用 pgvector 而用"的嫌疑。
> - **chunk 切分策略**：条款级切分（本项目已有 `clause_splitter`），而非固定 token 数切分——这是"条款检索"和"通用 RAG"的本质区别。
> - **这个能力属于【演进叙事】**（C5 落地），不是主线：M1–M4 的审查不依赖向量检索也能成立。避免让它绑架主线进度。

### C-D6 异步任务：arq（Redis 队列）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **arq** | 轻量、asyncio 原生、契合 FastAPI 异步栈 | 依赖 Redis | **首选** |
| Celery | 生态成熟 | 重、配置多 | 备选 |
| 线程池/进程池 | 零依赖 | 无持久化、无重试 | 不选（企业级要可靠） |

### C-D7 前端：React + TypeScript + Vite + Ant Design

## 八、风险与红线（架构师视角）

1. **合同数据敏感**：远程 API 只传必要字段，明确脱敏策略；本地解析**和本地 OCR 都不出域**（这是选 PaddleOCR 而非云 OCR 的根因）。
2. **LLM 幻觉是头号风险**：审查结果必须「规则引擎兜底 + 每条风险带原文定位」，不能只给结论。
3. **审批流并发冲突**：多人同时审批，用乐观锁（版本号）防覆盖。
4. **长合同超时**：分条款分段审查再聚合，而非一次性塞全文。
5. **「AI 只提示、法务裁决」的合规红线**：不做法律权威判定，最终由法务决定——这是企业级 AI 的正确姿势。
6. **语料形态断链**：坐标是承重墙。文本型/OCR 都能给坐标，只有「加密 PDF」会断——明确阻断并提示重传，**不静默降级**；DOCX 通过转 PDF 补齐坐标。每一份合同落库时都记录 `source_format` 与 `parse_confidence`，下游据此决定高亮/溯源的精度预期。

## 九、演进路径（什么时候升级什么）

| 触发条件 | 升级动作 |
|---|---|
| 合同量大、解析慢 | 引入分布式任务队列（Celery + 多 worker） |
| OCR 推理成为 CPU 瓶颈 | OCR 任务独立成 worker 池 / 换 GPU 推理 / 换更高精度模型（仍本地，不出域） |
| 相似条款检索量级增大 | pgvector → 独立向量库（Milvus/Qdrant） |
| 审批流变复杂（多分支、会签） | 手写状态机 → 引入 BPM（Flowable/Activiti，Java 生态） |
| 需要对外开放 | 加 MCP 适配层（复用 agentforge 的设计） |

## 十、大厂级场景模拟与技术债路线图（本项目核心增值）

> **一句话定位**：这个项目不仅是「合同审查业务」，更是一台**「大厂/互联网真实业务场景」的模拟器**——用来补上此前工作经历里没碰过的技术债（高并发、大数据量、异步消息、可观测）。这是本项目的第二价值主线。

### 10.1 模拟方法论：先造压力，再让技术长出来

大厂级场景的核心不是「把技术堆上去」，而是**先制造真实负载与约束，再让技术被迫长出来**。没有压力的高并发代码是死代码。

```
真实压力（压测工具 + 数据脚本）
        ↓ 逼出问题
慢查询 / 并发错误 / 消息堆积 / 瓶颈不明
        ↓ 针对性补技术
索引优化 / 限流熔断 / 削峰 / 可观测
        ↓ 用数据验证
QPS/延迟/错误率 的前后对比
```

**没有「压测」和「数据灌库」这两步，技术债清单就是空中楼阁。**

### 10.2 分布式的模拟方式：Docker 多容器

采用 **Docker Compose 多容器**模拟分布式（轻量、可复现、能真实踩到「单机遇不到」的坑）。后续需要真实网络/故障切换时再升级虚拟机。

| 容器 | 角色 | 补的技术债 |
|---|---|---|
| `api-1` / `api-2` | 无状态后端多实例 | 负载均衡、服务横向扩容、故障转移 |
| `nginx` | 网关/负载均衡 | 反向代理、限流入口 |
| `postgres-master` / `postgres-slave` | 数据库主从 | 读写分离、主从复制 |
| `redis` | 缓存/分布式锁 | 缓存一致性、分布式锁 |
| `kafka`（KRaft 单节点起步） | 消息队列 | 异步解耦、削峰、幂等 |
| `worker-1` / `worker-2` | 异步消费者 | 任务消费、水平扩容 |
| `observability` | Prometheus + Grafana + OTEL | 指标、链路追踪、告警 |

### 10.3 消息队列选型：Kafka（真实企业级）

**关键决策：不用轻量队列（arq/Redis），直接用 Kafka。** 理由——要补的是「真实大厂级」的异步能力，而非玩具 demo。Kafka 的分区、副本、消费者组、offset、消息堆积，正是「异步与消息队列」面试考点的核心。

Kafka 在合同审查里的真实用法（非 demo）：

| 用途 | 场景 | 补的技术债 |
|---|---|---|
| 审查流水线解耦 | 解析→抽取→规则→LLM 各步用 topic 传递 | 异步解耦、流水线 |
| 批量审查削峰 | 夜间批量审 10 万份合同，进队列慢慢消费 | 削峰填谷 |
| 结果异步通知 | 审批完成 → topic → 通知服务消费 | 事件驱动 |
| 审计事件流 | 所有操作进 topic，供审计/数据管道消费 | 事件溯源 |

> 注意：Kafka 本身是资源消耗点。起步用 **KRaft 单节点**（免 Zookeeper，省一半资源），32G 内存机器上精打细算。

### 10.4 技术债清单（四个方向，全部纳入）

| 方向 | 技术点 | 在合同审查里的真实落点 |
|---|---|---|
| **高并发保护** | 网关限流（令牌桶/滑动窗口） | 防突发流量打爆 LLM 账单 |
| | 服务熔断 + 降级 | 复用 agentforge 三重熔断，接真实场景 |
| | Kafka 削峰 | 批量审查错峰处理 |
| | 连接池调优 | DB/HTTP 连接池合理配置 |
| **大数据量** | 分库分表（按租户分片） | 查「某租户合同」不再全表扫 |
| | 索引优化 + 慢查询分析 | 用真实慢查询日志定位 |
| | 冷热分离 | 老合同归档对象存储，热数据留 PG |
| | 数据生命周期管理 | 定期归档 + 审计轨迹保留 |
| **异步与消息** | Kafka 生产者/消费者、分区/副本 | 流水线解耦 |
| | 幂等消费 | 防重复消费 |
| | 重试 + 死信队列 | 失败任务兜底 |
| | 消息顺序性/事务 | 审批状态流转不乱序 |
| **可观测与压测** | Locust 压测 + 容量基线 | 知道系统极限在哪 |
| | OpenTelemetry 链路追踪 | 定位「慢在哪一步」 |
| | Prometheus + Grafana | 指标 + 告警 |
| | 日志集中 | 排查分布式问题 |

### 10.5 分阶段路线：双轨 + 保底优先

> **核心纪律：业务闭环优先。技术债逐项注入，不追求一次性拉满（否则做不完，反而耽误求职）。**

```
轨道一（保底，先做完）——业务闭环
  阶段 0：合同审查核心功能跑通（单体即可）
          → 这是求职基本盘，先有这个

轨道二（技术债还债，逐项注入，每步有数据验收）
  阶段 1：Kafka 异步化（解耦 + 削峰，最核心）
  阶段 2：压测 + 限流熔断（高并发保护）
  阶段 3：分库分表 + 冷热分离（大数据量）
  阶段 4：可观测体系（贯穿始终）
```

**每一步的「可量化验收」，才是面试不露馅的硬料：**

| 阶段 | 验收数据（简历/面试素材） |
|---|---|
| 阶段 1 | 「审查流水线从同步 30s 阻塞 → 异步解耦，接口 <100ms 返回」 |
| 阶段 2 | 「压测 1000 并发，限流熔断后错误率从 X% → Y%，P99 延迟从 A → B」 |
| 阶段 3 | 「100 万合同数据，慢查询从 3s → 50ms（分库分表 + 索引）」 |
| 阶段 4 | 「链路追踪定位到 LLM 调用占 80% 耗时，针对性优化」 |

### 10.6 硬件的现实约束与应对

| 约束 | 应对 |
|---|---|
| i7-6700K 单 CPU，多容器共享 | 压测目标是「验证架构行为正确」，而非「真实大厂 QPS 数字」 |
| 32G 内存，Kafka + PG + Redis + 后端多实例 | KRaft 单节点 Kafka、PG 主从起步、按需起 worker |
| 单机测不出真实网络抖动/硬件故障 | 用 Docker 网络隔离 + 手动 kill 容器模拟故障 |

> **诚实结论**：虚拟机/Docker 模拟的价值，不是「压出真实 QPS」，而是「真实经历分布式系统的故障与一致性坑」（脑裂、主从切换、重复消费、超时重试）——这些才是大厂经验里最值钱、最缺的部分。
